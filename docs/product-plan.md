# Архитектура и план развития Forma CMS

Forma должна позволять владельцу бизнеса самостоятельно менять сайт и добавлять функции через диалог. Основной пользовательский сценарий: выбрать место на странице, описать задачу, приложить материалы, увидеть работающий результат и опубликовать его. Для обычных правок остаются понятные поля и визуальный редактор. Технические операции скрыты за этими действиями, но исходники принадлежат владельцу и доступны разработчику.

Первый локальный MVP уже реализован в этом репозитории. Далее описаны подходы существующих CMS, целевая архитектура и последовательность развития. Запланированные возможности явно отделены от текущей реализации. Источники проверены 19 октября 2026 года.

## Подходы существующих CMS

| Система | Как работает редактирование | Что применить в Forma |
| --- | --- | --- |
| Nuxt Studio | Визуальный редактор Markdown, формы для YAML/JSON и отдельный режим исходников. Результатом остаются файлы контента. | Один источник данных для ручного редактора и агента; пользователю не нужно понимать формат файла. [Документация](https://nuxt.studio/content) |
| TinaCMS | Контент по схеме и визуальное редактирование рядом с React-сайтом; `useTina` обновляет данные страницы. | Предсказуемые схемы блоков и обратная связь в контексте страницы. Наш протокол preview должен быть независим от React. [Документация](https://tina.io/docs/contextual-editing/overview) |
| Payload | Панель открывает приложение в iframe и передаёт изменения через `postMessage`; доступны подходы для клиентского и серверного рендеринга. | Отдельное происхождение preview, адаптер обновления и режимы ширины экрана. [Документация](https://payloadcms.com/docs/live-preview/overview) |
| Sanity | Visual Editing связывает preview, переход к полю по клику и перестановку секций; есть интеграции с Nuxt и Next. | Стабильное соответствие элемента страницы полю контента, а позднее — позиции в исходниках. [Документация](https://www.sanity.io/docs/visual-editing/introduction-to-visual-editing) |
| Directus | Коллекции и поля отражают структуру базы; Flows связывают события с операциями обработки данных. | Формы, заявки и интеграции должны иметь явную модель данных и журнал исполнения. [Модель](https://docs.directus.io/app/data-model), [Flows](https://docs.directus.io/app/flows) |

Общий полезный принцип — структурированный контент, независимый frontend и контролируемая публикация. Для Forma этого недостаточно: новый калькулятор, CRM-интеграция или серверный обработчик требуют изменений кода. Поэтому предлагаемая архитектура объединяет CMS и среду разработки агента. Готовый headless CMS можно использовать для данных, но он сам по себе не решит безопасное выполнение изменённого приложения.

## Работа владельца сайта

При первом подключении разработчик или агент определяет фреймворк, команду сборки, маршруты, источники контента и компоненты. Владелец видит сайт, разделы «Материалы», «Заявки», «Интеграции» и историю. Git, команды сборки и инфраструктурные ошибки доступны в технических подробностях.

Обычный запрос выглядит так: «Добавь форму расчёта ремонта после услуг. Поля: площадь, тип квартиры, телефон. Заявки отправляй в CRM». Владелец может приложить PDF с прайсом, логотип, фотографии и пример оформления. Агент учитывает выбранную секцию, существующий стиль и предыдущие сообщения. Если необходим адрес CRM или ключ, интерфейс открывает конкретное поле подключения; ключ не предлагается писать в чат.

После выполнения интерфейс сообщает результат понятным языком: «Добавлена форма из трёх полей. Заявки сохраняются. Для CRM осталось подключить аккаунт». Preview показывает новую функцию и позволяет её проверить. Публикация — отдельное действие с указанием версии. Ошибка сборки сохраняет прежний опубликованный сайт и предлагает исправить черновик.

Ручные изменения используют ту же модель: клик по заголовку открывает текстовое поле, клик по изображению — библиотеку материалов. Новые компоненты, созданные агентом, должны регистрировать редактируемые поля, чтобы их дальнейшее обслуживание также не требовало кода. Для неописанного компонента доступен запрос агенту; универсальное распознавание произвольной вёрстки не обещается.

## Модель проекта

В целевой версии проект содержит страницы, блоки, материалы, подключения, диалоги, задачи агента и публикации. У страницы есть стабильный ID, маршрут, SEO и упорядоченные блоки. У блока — тип, версия схемы, свойства и связь с компонентом Vue либо React. ID сохраняется при переименовании и перестановке.

Исходники сайта и файловый контент хранятся в GitLab. PostgreSQL хранит пользователей, роли, задания, ссылки на ревизии, заявки и журнал событий. Объектное хранилище хранит материалы и результаты сборки. Секреты находятся в отдельном хранилище, доступны по ссылке на подключение и не попадают в Git или контекст модели.

Ревизия проекта связывает конкретный commit, снимок контента, manifest материалов и набор подключений. Публикация ссылается на одну проверенную ревизию. Изменение в чате и ручная правка используют optimistic concurrency: если основа устарела, система не затирает более свежую работу. Откат выбирает предыдущий артефакт; восстановление для дальнейшего редактирования создаёт новый черновик.

В локальном MVP эту роль выполняет `.data/project.json` с атомарной записью, очередью мутаций и номером ревизии. Сайт пока одностраничный; файловый контент — `content.json`, стили — `styles.css`, поведение — `script.js`.

## Подключение Nuxt и Next

Целевая интеграция состоит из небольшого общего SDK, модуля Nuxt и пакета Next. Общий протокол описывает страницы, схемы блоков, изменение draft, выбор элемента, состояние сборки и проверку готовности. Само приложение продолжает использовать привычные Vue/React-компоненты.

Предлагаемый `forma.config.ts` указывает пути контента, реестр компонентов, маршруты, команды проверки и допустимые точки расширения. Nuxt-модуль подключает preview и серверные обработчики через Nuxt/Nitro. Next-адаптер использует draft mode, серверную загрузку контента и обновление клиентского preview. Детали API адаптеров предстоит проверить на поддерживаемых версиях фреймворков при реализации.

Для готового проекта CLI сначала создаёт ветку подключения и отчёт: обнаруженные маршруты, поддержанные компоненты, нестандартные участки. Существующие компоненты не переписываются без необходимости. Подключение считается готовым после успешной исходной сборки и проверки хотя бы одной ручной и одной агентной правки.

Сейчас MVP экспортирует самостоятельные Nuxt/Next-проекты в ZIP. Это переносимый сайт с редактируемыми файлами и медиа. Подключение произвольного действующего репозитория и синхронизация с ним ещё не реализованы. Формам в экспортированном проекте нужен собственный backend endpoint.

## Выполнение задач агента

Целевой цикл задачи:

1. Сохранить сообщение, ссылки на вложения, выбранную страницу и исходную ревизию.
2. Создать изолированную рабочую копию сайта и загрузить только необходимый контекст.
3. Прочитать файлы и схемы, составить последовательность изменений. Вопрос владельцу нужен только при существенной неопределённости или недостающем подключении.
4. Изменить контент, Vue/TSX-компоненты, стили, обработчики и декларации интеграций в этой копии.
5. Выполнить проверку схем, типов, сборку, функциональные тесты изменённой функции и browser smoke test.
6. При ошибке выполнить ограниченное число исправлений; затем показать понятную причину и сохранить диагностику.
7. Подготовить preview, краткое описание результата и технический diff. Применить к черновику только при актуальной исходной ревизии.
8. После публикации владельцем продвинуть проверенный артефакт в production и сохранить возможность отката.

В MVP агент уже работает с отдельной копией, реальными инструментами чтения и записи, отменой, ограничением времени и валидацией перед применением. Он меняет JSON/HTML/CSS/JavaScript и подключения. Shell, установка npm-пакетов и произвольные серверные файлы пока недоступны. Для этого нужен отдельный runner, а не расширение прав основного процесса CMS.

## Вложения и память диалога

Материал загружается отдельно от отправки сообщения. Сервер проверяет тип и размер, присваивает ID, сохраняет оригинал и связывает его с сообщением. Модель получает изображение/PDF либо текстовые порции через инструмент чтения. Материалы сайта и временные референсы имеют общий каталог, но разное использование: публичным ресурс становится после включения в сайт.

В следующих версиях появятся извлечение текста Office, OCR, миниатюры, антивирусная проверка, дедупликация по хешу и ограничения на стоимость обработки. Текст вложения считается данными пользователя; инструкции внутри документа не могут расширить инструменты или права агента. Долгие диалоги потребуют краткой памяти решений и выборочного чтения истории, чтобы не отправлять все файлы при каждой правке.

## Формы и интеграции

Форма описывает поля, ограничения, сообщение об успехе и действия после отправки. Отправка сначала надёжно сохраняет заявку, затем запускает доставку. Недоступность CRM не должна терять заявку. Целевой сервис доставки использует очередь, повторные попытки с задержкой, idempotency key и журнал результата без секретов.

Для распространённых подключений нужны готовые адаптеры: CRM, email, Telegram, аналитика, webhook. Агент выбирает адаптер и создаёт настройки, а владелец подключает аккаунт в специальной форме. Произвольный внешний скрипт показывает домены, назначение и какие данные он получает. Изменение адреса подключения требует заново привязать секрет, чтобы ранее сохранённый ключ не ушёл другому получателю.

MVP сохраняет заявки локально и доставляет их в включённые HTTPS webhooks. Новая или изменённая агентом интеграция выключена до просмотра. Browser-скрипты подключения выполняются в опубликованной версии после включения. Очереди повторной доставки пока нет.

## Авторизация ИИ и пользователей

Вход в CMS и подключение модели — разные учётные связи. В SaaS владелец входит в свою организацию, затем подключает провайдера ИИ. Права редактирования и публикации определяет CMS, а доступ к моделям — провайдер.

Текущий прототип реализует официальный Sign in with ChatGPT для локального сценария: регистрация приложения, PKCE, `state`, `nonce`, проверка ID token и обновление токенов. Токены остаются на сервере. Публичный OSS-путь нельзя автоматически считать разрешением для коммерческого hosted CMS; доступ для такого продукта нужно согласовать до запуска. Альтернатива — собственный API-ключ владельца. [OAuth](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [ограничения](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).

При недоступности модели CMS сохраняет все ручные функции. Переход на платный API не выполняется автоматически. Live-вход и фактическая генерация ещё требуют проверки с аккаунтом владельца; протокольные тесты используют тестовые ответы.

## Изоляция и инфраструктура

Runner для произвольного кода запускает каждую задачу в отдельном контейнере или microVM с лимитами CPU, памяти, диска и времени. Внутри нет Docker socket, ключей CMS и production credentials. Получение зависимостей и доступ к сети контролируются отдельно; секреты для работы интеграций передаёт backend, а не модель.

Preview и опубликованные сайты должны находиться на отдельных доменах от Studio. Сообщения iframe проверяются по origin и типу; токены Studio не доступны коду сайта. Для production нужны роли owner/editor/publisher, tenant isolation, аудит, защита входа, резервное копирование и проверка восстановления. Локальный MVP слушает только loopback и не предназначен для размещения в интернете без этого слоя.

Основной GitLab-репозиторий пока один: продукт, тесты, документация и CI. Разделять его на множество репозиториев до появления независимо выпускаемых SDK нет необходимости. Репозитории сайтов будут отдельными, с ограниченными токенами на один проект. Задача агента создаёт ветку, публикация связывается с commit и артефактом.

## Этапы и критерии готовности

| Этап | Результат | Критерий готовности |
| --- | --- | --- |
| Локальный MVP — реализован | Studio, ручные правки, чат, вложения, формы, интеграции, версии, исходники и экспорт | Проверки API и сборка Studio; live AI проверяется отдельно после входа |
| Проверка продуктового сценария | Реальная работа с ChatGPT/API и 10–15 типовыми задачами владельца | Текст, новая форма, CSS, интерактивный блок и webhook проходят цикл preview → публикация → откат; сохраняются ошибки и стоимость |
| Многостраничность и адаптеры | Маршруты, схемы блоков, CLI подключения Nuxt/Next | Одна действующая Nuxt- и одна Next-кодовая база подключаются без ручного копирования контента |
| Runner и GitLab | Изменение Vue/TSX/backend, установка зависимостей, сборка preview | Ошибочный код не попадает в production; отмена освобождает окружение; воспроизводимая сборка и безопасный откат |
| Hosted пилот | Авторизация, несколько организаций, домены, очереди и секреты | Проверена изоляция проектов, восстановление бэкапа, доставка заявок при сбоях, лимиты расходов |
| Продукт для бизнеса | Онбординг, библиотека подключений, тарифы, эксплуатация | Владелец самостоятельно выполняет ключевые задачи; измеряются время до публикации, доля успешных задач и обращения за помощью |

Порядок отражает зависимости. Сначала нужно подтвердить удобство и качество агентных правок, затем расширять исполнение и запускать hosted-сервис. Точные сроки зависят от состава команды, поддерживаемых интеграций и доступа к провайдеру; до проверки пилотных задач фиксировать их было бы ненадёжно.
